That&#x27;s not what prevents you from running into bugs. The bugs come when you treat null and undefined as equivalent and try to pass them into a function with default params, without knowing which one you have. Because the defined behaviour of default params is different for null and undefined.<p>For example, say you have a data type of &#x27;null or [0...11]&#x27; for a month input the user may or may not have interacted with yet. It gets passed around a bit and ends up going through a function defined with default params, like &#x27;function doSomethingWithDate(day = 0, month = 0, year = 1900)&#x27;, and in that function there&#x27;s a null check like &#x27;if day, month or year is null, do whatever we want to do if the user hasn&#x27;t entered a date yet&#x27;.<p>A few months later someone picks up a ticket to refactor the date input, and they use &#x27;undefined or [0...11]&#x27; for the month instead, which doesn&#x27;t matter because your team always just checks both with things like &#x27;==&#x27;, &#x27;!=&#x27; or &#x27;??&#x27;.<p>Except surprise, it does matter, because now something somewhere else breaks because it thinks the state is &#x27;the user has entered 1&#x2F;1&#x2F;1900&#x27; instead of &#x27;the user hasn&#x27;t entered anything yet&#x27;.<p>Of course you might not run into this specific bug, because the code is a bit contrived, and most good programmers will recognise that whatever &#x27;doSomethingWithDate&#x27; is it probably doesn&#x27;t need to be run unless the user has actually entered a date already. That null check should be happening as close to the user input as possible, and there shouldn&#x27;t really be any room for people to use default params between those two places.<p>The problem is that in the real world people write dogshit code like this <i>all the fucking time</i>. That would rate at about the 5th percentile of all the garbage code I&#x27;ve seen in my career.<p>My point is that that&#x27;s literally impossible to run afoul of language differences between null&#x2F;undefined if you&#x27;re strictly using either null or undefined, as opposed to this blase mindset of &quot;just always check for either&quot;, because you now know what your data type is while you&#x27;re writing the code, and can look up the standard library or 3rd party library docs to see how they interpret it. If you have data types of &#x27;null or undefined or ...&#x27; then you don&#x27;t know which one you&#x27;ve got until runtime and you need to account for both possibilities everywhere. That means coercing it into either specifically null or undefined every single time you want to pass it to a library function, your own codebase&#x27;s functions that use default params, or any other place the language itself treats undefined and null in different ways.<p>Always use the minimal data type for representing whatever you need. If you don&#x27;t then you&#x27;re literally choosing to have ambiguity in your code base. It makes no sense.<p>Also this:<p>&gt; You could just as easily run into a bug with 3rd party lib code by distinguishing between the two when that library doesn&#x27;t.<p>...is nonsense. If the library doesn&#x27;t distinguish between the two then by definition it cannot matter which one you pass in, since it&#x27;s treating them the same.')
