Item(by='jcranmer', descendants=None, kids=None, score=None, time=1612412978, title=None, item_type='comment', url=None, parent=26022376, text='When you develop compilers, you generally have a three-way tradeoff that you can&#x27;t get all three of simultaneously: runtime speed, generated code size, and compile time. For what&#x27;s effectively a peephole pass, the main balance question is if the increase in runtime speed is going to be worth the extra time compiling the code. If patterns don&#x27;t crop up very frequently, and the resulting code has only marginal speedups, then it&#x27;s not going to be worth slowing everyone&#x27;s compile time for that speedup.<p>In the context of LLVM IR, there&#x27;s a subtle issue which is even more important. LLVM IR is sufficiently divorced from actual hardware instructions to be a good basis for a cost model. I believe Souper is largely using instruction count as its cost model [1], which is going to really fall down when you handle i1 values, since most processors aren&#x27;t capable of doing arithmetic on i1 values natively, and converting the result of a comparison instruction into one that can be reasoned about with boolean circuits can involve several extra instructions.<p>[1] Regehr&#x27;s original blog post on the matter says instructions are cost 1, constants and phis cost 0, and selects and div&#x2F;rem cost 3. sexts&#x2F;zexts&#x2F;truncs aren&#x27;t explicitly modeled, and so also presumably cost 0. So it&#x27;s mostly instruction cost.')
