Item(by='brucehoult', descendants=None, kids=[26011067], score=None, time=1612325317, title=None, item_type='comment', url=None, parent=26006610, text='What I&#x27;m hearing in this post is &quot;Where RISC-V uses a smaller field size for something than ARM64 they have under-provisioned and will need extra instructions, and where RISC-V uses a larger field size for something than ARM64 it will never be used and is wasted&quot;.<p>In other words, ARM&#x27;s architects chose every parameter correctly, and RISC-V&#x27;s chose every parameter badly.<p>It <i>might</i> be true, but you kind of have to prove it, not just assert it.<p>Take the J&#x2F;JAL vs B&#x2F;BL range for example. It&#x27;s not just embedded. Look through your Linux distro&#x27;s binaries and you&#x27;ll find <i>very few</i> with TEXT size over 2 MB.<p>One of the few on my (x86_64, but it doesn&#x27;t really matter) system is &#x2F;opt&#x2F;google&#x2F;chrome&#x2F;chrome with 159,885,517 bytes.<p>That exceeds ARM64&#x27;s single-instruction BL range, as well as RISC-V&#x27;s.<p>A quick analysis shows that of the 373500 callq instructions in the binary, statically 55.53% fall within the RISC-V single-instruction range, 100% fall within the ARM64 range. Dynamically I don&#x27;t know, but I suspect the percentage that fall in the RISC-V range would be a lot higher.<p>Anyway .. code size. The extra AUIPC instructions needed in the RISC-V program will make it around 648 KB or 0.4% larger than the ARM64 program.<p>That&#x27;s a pretty far cry from &quot;I would estimate this one issue alone will result in a ~5-10% code size increase&quot; you state. I mean -- that&#x27;s a factor of 12x to 25x different than you state.<p>But wait there&#x27;s more.<p>One reason that RISC-V JAL offsets are limited is that 2 bits out of 32 are taken up by indicating whether the current instruction is 4 bytes or 2 bytes in size.<p>So that&#x27;s a waste right?<p>It would be if you didn&#x27;t use it. But RISC-V does use it. In a typical RISC-V program, around 50% to 60% of all instructions use a 2 byte opcode, giving a 25% to 30% reduction in code size.<p>On the same 152 MB program (Chrome) where not having long JAL offsets costs 0.6 MB of code size, the C extension will probably save around 40 to 45 MB of code size.<p>That seems like a pretty good trade to me.<p>What will the speed effect of those extra AUIPC instructions be? I don&#x27;t know. I&#x27;d have to instrument Chrome and run it at a fraction of normal speed to find out.<p>That&#x27;s definitely something that should be done before making a pronouncement that one ISA is definitely better and the other one made all the wrong trade-offs.<p>However, my experience of analyzing smaller programs is that the dynamic penalty (execution speed) is typically much less than the static penalty (code size). At a wild guess, I&#x27;d go with four times less, or 0.1%.<p>That&#x27;s in the noise.<p>Might a RISC-V core be enough simpler than a comparable ARM64 core to clock 0.1% faster? Could well be. Might it be enough simpler to be 0.1% smaller and thus cost 0.1% less in die space -- or allow you to put 0.1% more cores on the same chip? Could well be.<p>Even the detractors don&#x27;t argue that RISC-V isn&#x27;t simpler. &quot;It&#x27;s <i>too</i> simple&quot; they say, takes purity and orthogonality too far.<p>Maybe, but you need to prove it, not just assert it.')
