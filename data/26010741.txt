Program code should be comprehensible as plaintext. This is why I&#x27;m not a fan of overuse of the `var` keyword in C# - or `auto` in C++. (Many people feel forced to use `var` and `auto` in C# and C++ respectively when their program uses horribly complicated generics or template instantiations - this wouldn&#x27;t be necessary if C# permitted more flexibility with type-aliases.<p>&gt; List is the general concept of a List in Java<p>But that&#x27;s a huge design-issue in itself: Interfaces should not describe what something &quot;is&quot;: they should describe what something is <i>capable of</i> - this is doubly essential when using reified generics because of type parameter variance (Java skirts this one because of type-erased generics - which is another discussion). A distinct advantage of interfaces describing capabilities is the &quot;I&quot; prefix can be replaced with a rule requiring interface names to be adjectives (i.e. class&#x2F;struct = noun, method = verb, interface = adjective+noun).<p>Rather than having this (invariant) interface:<p><pre><code>  interface List&lt;T&gt; {\n    void add( T item );\n    void remove( T item );\n    int length { get; }\n    T get( int index );\n  }\n  </code></pre>\nWe&#x27;d have these variant interfaces:<p><pre><code>  interface ReadableList&lt;out T&gt; {\n    int length { get; }\n    T get( int index )\n  }\n\n  interface MutableBag&lt;in T&gt; {\n    void add( T item )\n    void remove( T item )\n  }\n</code></pre>\nWhich is great because then we can do type-safe stuff like this:<p><pre><code>  class Vector&lt;T&gt; implements ReadableList&lt;T&gt;, MutableBag&lt;T&gt; {\n     &#x2F;&#x2F; etc\n  }\n\n  class Employee extends Person {}\n  class Boss extends Employee {}\n\n  Vector&lt;Employee&gt; list = new Vector&lt;Employee&gt;();\n  ReadableList&lt;Person&gt; people = list;\n  MutableBag&lt;Boss&gt; appendOnlyBossesFromHere = list;</code></pre>')
