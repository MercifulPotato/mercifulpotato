Item(by='lmeyerov', descendants=None, kids=None, score=None, time=1612397368, title=None, item_type='comment', url=None, parent=26020657, text='FWIW, you can support tensors etc. natively today by using Arrow&#x27;s structs, such as `column i_am_packed: {x: int32, y: int32, z: int32, time: datetime64[ns], temp: int32}`. This will be a dense, packed representation for whatever fixed type the column has, including dynamically generated. It ends up being quite nice to have that passed around, esp. vs say protobufs.<p>You wouldn&#x27;t be sending mixed-length values, and ~all metrics systems I&#x27;ve worked with would be fine there. The nullables end up a win for those. However, you&#x27;d need to do a manual (likely zero-copy) casts between the struct-type to whatever tensor-type you&#x27;re using. Massively popular ml systems like huggingface do this fine afaict for their Arrow-based tensor work. Likewise, as we do a lot of GPU stuff, what&#x27;s additionally common is compacting the in-memory stuff as big memory blocks (&#x27;long recordbatches&#x27;) instead of CPU-land&#x27;s typically more fragmented ones, and that ends up making casts even easier. Annoying to have to add an explicit cast for some interop cases, but preserves end-to-end type safety &amp; hasn&#x27;t been a deal breaker for us. Having to write the cast being annoying&#x2F;difficult, esp. for whoever does it first.<p>More frustrating for us has been sparse data and compression controls, but most formats are even worse here..')
