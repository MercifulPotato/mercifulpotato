Item(by='sbauch', descendants=None, kids=None, score=None, time=1612285050, title=None, item_type='comment', url=None, parent=26003171, text='Thanks so much!<p>A useful framework for thinking about SAML vs OAuth from an engineer&#x27;s perspective is to think of OAuth as class based, while SAML is instance based.<p>When you set up a new OAuth provider such as Github you typically grab a Client ID and Secret, specify your redirect URIs, and once your integration is complete any Github user can sign in with a Sign in with Github button.<p>But with SAML, you need to perform configuration with each customer&#x27;s Identity Provider instance. As you pull on this thread you start to see where the challenge with SAML lies. SAML as a protocol isn&#x27;t super complicated, and tons of OSS already exists to perform authentication. But you need to create and persist configuration data for each of your customers, which suggests needing a UI to perform this onboarding. You need to help your customer configure your app in their IDP, so you&#x27;ll want to create documentation. And you need to adjust your sign in flow - you can&#x27;t just stick a Sign in With Okta button, you need to ascertain from the user which IDP they use for authentication.<p>Osso though handles all of the &quot;instance based&quot; challenges, and allows your app to use OAuth to communicate with your Osso instance.')
