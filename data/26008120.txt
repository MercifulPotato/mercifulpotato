Item(by='Kranar', descendants=None, kids=[26008248, 26012521], score=None, time=1612306223, title=None, item_type='comment', url=None, parent=26006280, text='Long variable names don&#x27;t help either. It&#x27;s been mostly a stylistic choice and a recent trend that stylistically long variable names are nice. But there are plenty of projects that use short variable names or even one letter names, and I don&#x27;t see any evidence that those projects are less productive because of it.<p>The actual research is that long variable names make it harder to understand code. It makes the variable name become an integral part of any code snippet that a reader feels compelled to memorize the specific names used, and that memorization results in errors and increased recall time.<p>Short variable names, including single letter names, allow a reader to basically ignore the name itself which allows them to accurately memorize an entire chunk of code without feeling the need to memorize long names. This improves recall time.<p>In simpler terms, when a snippet of code uses descriptive variable names your brain is inclined to believe that those names matter and that you need to remember them, compared to short variable names that your brain will not have to bother remembering and instead frees you up to focus on the structure and semantics of the code snippet.<p>The study that you can read, which is quite insightful is here:<p><a href="https:&#x2F;&#x2F;pdf.sciencedirectassets.com&#x2F;271600&#x2F;1-s2.0-S0167642309X00055&#x2F;1-s2.0-S0167642309000343&#x2F;main.pdf" rel="nofollow">https:&#x2F;&#x2F;pdf.sciencedirectassets.com&#x2F;271600&#x2F;1-s2.0-S016764230...</a><p>Note that long function names DO help, but long variable names do not.<p>That said, feel free to use long variable names if that&#x27;s what you like and your project does it that way. Don&#x27;t, however, express that as some kind of extensively studied software engineering principle that has research backing it. It&#x27;s basically one of those things someone decided was true and everyone else just decided to believe it without ever doing the kind of work needed to validate the hypothesis.<p>In software engineering, we are still in the days of Aristotle, where we simply believe things to be true because we want them to be true. Just like the days of Aristotle I wouldn&#x27;t be surprised if it takes us literally thousands of years before someone comes along and decides to question and test basic assumptions we all take for granted.')
