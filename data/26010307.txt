Item(by='lewisl9029', descendants=None, kids=[26010720], score=None, time=1612323149, title=None, item_type='comment', url=None, parent=26010196, text='I think that&#x27;s certainly a valid approach, and comes with a ton of benefits. But I don&#x27;t think that has to be the _only_ viable approach to use a state machine in React without having to worry about subtle synchronization bugs.<p>Especially since even if our endgame is to go all-in on the state machine as our only source of truth for state, we could still benefit from a smooth transition path to get there.<p>Using state machines deliberately for complex flows while delegating simpler state management tasks to simple useState hooks should ideally be just as robust and well supported as modeling our entire UI as a giant state machine.<p>At the end of the day, the state machine definition in both of these libraries is just a bunch of data, to be interpreted by some runtime that&#x27;s responsible for maintaining internal state and reacting to events. Currently that runtime is a generic stateful &quot;service&quot; implementation provided by these libraries, but there&#x27;s no reason why that runtime couldn&#x27;t be some stateful service implementation built on top of React, or any other view layer with its own opinions on state management.')
