Item(by='IcePic', descendants=None, kids=[25998609], score=None, time=1612253163, title=None, item_type='comment', url=None, parent=25998180, text='It will cost a cycle or three extra, but given the great cost to make syscalls in the first place (especially if you have to do flushes and mitigations for the &#x27;recent&#x27; security bugs on x86) it probably won&#x27;t matter much. 1000 vs 1003 or 10000 vs 10003 would be hard to measure in a real world program.<p>Also, many things libc does (which go programs need to do themselves) is to wrap a lot of the calls to things like malloc&#x2F;calloc&#x2F;realloc to use internal buckets and as seldom as possible call out to the kernel to get one or ten pages of ram in one call, then hand out suballocations from them for each &quot;obj = malloc(8);&quot; so that you minimize the amount of syscalls made, regardless of if you do them directly or via libc.<p>Since syscalls always were expensive (you need to save registers, check userid permissions, flip to kernel mode, do the work asked for with or without SMP locking protections, give permissions to uid for the resource returned, perhaps check if its time to deliver signals or switch to another process and if not, flip out of kernel mode, restore registers and return to the process again) a lot of the calls done by a C program is kept in libc if possible.<p>For example, gettimeofday() springs to mind, where a lot of trickery is done to give all programs a readonly page with the current time mapped into your program space so the call doesn&#x27;t have to go via the kernel but instead becomes a memory read, since programs tend to call this thousands of times.')
