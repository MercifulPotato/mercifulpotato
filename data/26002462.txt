Item(by='captainmuon', descendants=None, kids=[26006185], score=None, time=1612281349, title=None, item_type='comment', url=None, parent=26001179, text='One thing I rarely see discussed - and one of the reasons I don&#x27;t like Wayland personally - is the second order effect of putting everything in the compositor: It is now really hard to write a &quot;window manager&quot; or window tools. And this leads to a certain uniformity of desktop environments (the big ones, GNOME + Plasma, and then a bunch of keyboard driven minimal environments &quot;for hackers&quot;)<p>What I mean is, back in the day with X11, all clients were equal and there were nice little tools that let you switch between virtual desktops graphically (desktop pagers). I myself wrote a little taskbar (with the kind of glow animation that moves with the cursor that Windows 7 made popular), but never published it unfortunately. A lot of people wrote or hacked on window managers. It was never really easy, but at least it was possible.<p>Now with wayland, you have to write not only the code that draws the titlebars, but the code that puts the pixels on the screen, input handling, clipboard handling and all kinds of stuff.<p>Of course you can fork an existing window manager, or use something like wlroots, but they are all opinionated. If you just want &quot;GNOME with different titlebars&quot; someone else wants &quot;KDE with different titlebars&quot; - you&#x27;re out of luck. So this makes the barrier to entry really high.<p>On the other hand, if somebody would write a &quot;window decorator&quot; interface, you could write a small window decorator process (like we had with Compiz). I don&#x27;t believe this will happen, because it would have to be adopted by multiple compositors to make sense. If it did, I would have a bunch of ideas I&#x27;d like to try out one day.')
