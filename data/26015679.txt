Item(by='0xbadcafebee', descendants=None, kids=None, score=None, time=1612371397, title=None, item_type='comment', url=None, parent=26010215, text='Default configuration exists for multiple reasons: 1) to provide minimally working software so that the user isn&#x27;t burdened by unnecessary configuration, 2) to facilitate easier testing of minimal functionality, 3) to keep configuration DRY, and 4) to stop-gap missing configuration.<p>Of those, only 4) relates to typing. But even then it often bears no relation to real typing, because often there&#x27;s no schema or typing at all, and usually application has no idea what version a given configuration relates to.<p>In addition to achieving the above 4 points, we also need to be able to differentiate between default and modified configuration, so the application can override defaults successfully. You can keep default and modified configs separate a number of ways. You can hard-code it in the application, which is fine for the application. But it&#x27;s a pain in the ass for the user. And as a packager, you cannot expect files in &#x2F;etc&#x2F; to always be &quot;defaults&quot;, as the user&#x2F;administrator expects these to be configured by themselves at any time. And if you want to upgrade software, there needs to be a way to differentiate the versions of default configuration to compare the modified configuration to.<p>The best way to do this is to package default configuration in &#x2F;usr&#x2F;share&#x2F;. The user then has the job of upgrading their modified configuration in &#x2F;etc&#x2F;, and they can use &#x2F;usr&#x2F;share&#x2F; as a reference, in combination with some UPGRADING guide.<p>Distros have long had a convention to package a default distro-specific configuration in &#x2F;etc&#x2F;, so that when the app first starts, it can work out of the box. But then when you&#x27;d upgrade a package, the distro would have to figure out what to do with the once-default-but-now-modified files in &#x2F;etc&#x2F;. This just adds unnecessary burden on the distro. Instead, the user needs to look at their own manual configuration and update it if necessary. But the default configuration for the system should remain virgin and independent, in &#x2F;usr&#x2F;share&#x2F;.<p>And of course, none of this applies to configuration that <i>can&#x27;t</i> be default. The application should always die if it doesn&#x27;t find required configuration.')
