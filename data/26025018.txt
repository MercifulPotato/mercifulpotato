Item(by='chriswarbo', descendants=None, kids=None, score=None, time=1612444347, title=None, item_type='comment', url=None, parent=26024255, text='We can think of &quot;data&quot; as simply deferring a choice&#x2F;branch. For example consider this code:<p><pre><code>    boolean function1(...) {\n      FOO\n      return true;\n    }\n\n    void function2(...) {\n      BAR\n      if (function1(...)) {\n        BAZ\n      } else {\n        QUUX\n      }\n    }\n</code></pre>\nThe boolean lets us separate <i>how to make a decision</i> (which we define in function1), from <i>how to handle a decision</i> (which we define in function2). We can always eliminate this data by bringing those two things together, e.g.<p><pre><code>    &#x2F;&#x2F; Inline function1 into function2\n    void function3(...) {\n      FOO\n      BAR\n      if (true) {\n        BAZ\n      } else {\n        QUUX\n      }\n    }\n\n    &#x2F;&#x2F; Simplify the if&#x2F;then&#x2F;else\n    void function4(...) {\n      FOO\n      BAR\n      BAZ\n    }\n</code></pre>\nOf course, it&#x27;s very useful to keep things separate and to pass data around (modularity, readability, etc.). My point is that the computer&#x2F;language doesn&#x27;t care about these things, so we can use refactorings like this to &#x27;distill the essence&#x27; of what data &#x27;really is&#x27; (from this one perspective, at least).<p>So what <i>can</i> we do with a boolean?<p>- We can discard it. Such code can always be refactored to eliminate the boolean (it&#x27;s dead code).<p>- Pass it to some other code. We can always refactor this to remove such intermediate steps, e.g. above we inlined &#x27;function1&#x27; to avoid passing the boolean around.<p>- Construct them. We do this by using the &quot;constructors&quot; &#x27;true&#x27; or &#x27;false&#x27;, AKA the &quot;introduction forms&quot;.<p>- Branch on them using if&#x2F;then&#x2F;else. This is also called &quot;destructing&quot;, where if&#x2F;then&#x2F;else is a &quot;destructor&quot; or &quot;elimination form&quot;.<p>- Simplify &#x27;if(true) ...&#x27; and &#x27;if(false) ...&#x27;. Here we are &#x27;destructing a constructor&#x27;, which can always be replaced by the relevant branch.<p>If we apply these refactorings over and over we can eventually simplify-away <i>every</i> boolean value in a program. There are a couple of things to keep in mind:<p>- Some languages have special-case boolean operations like &#x27;!foo&#x27;. Those are equivalent to functions containing branches, which can be refactored as above, e.g.<p><pre><code>    boolean not(boolean x) {\n      if (x) {\n        return false;\n      } else {\n        return true;\n      }\n    }\n\n    boolean and(boolean x, boolean y) {\n      if (x) {\n        return y;\n      } else {\n        return false;\n      }\n    }\n\n    boolean or(boolean x, boolean y) {\n      if (x) {\n        return true;\n      } else {\n        return y;\n      }\n    }\n\n - To fully eliminate data, we need to include any &#x27;external&#x27; code, e.g. &#x27;inlining&#x27; external libraries, system calls, third-party APIs, etc. For simplicity I&#x27;ll just assume we&#x27;re using a single program in a single language, but the principle still holds in general.\n</code></pre>\nNote that inlining intermediate steps and removing unused parameters have nothing to do with booleans themselves; they apply to all forms of data. Hence the &#x27;essence&#x27; of booleans is the simplification of &#x27;if(true)...&#x27; and if(false)...&#x27;.<p>We can do this with booleans since they are a &quot;sum type&quot;, i.e. there are a few distinct forms of boolean (namely &quot;true&quot; and &quot;false&quot;). This is similar to the article&#x27;s &quot;Shape&quot; type, which has a &quot;Circle&quot; form and a &quot;Rectangle&quot; form.<p>OOP languages don&#x27;t tend to support sum types directly; instead we can &#x27;fake it&#x27; using subtypes. Here&#x27;s an example, where I&#x27;ve implemented the simplification behaviour using subtype polymorphism:<p><pre><code>    abstract class Boolean {\n      T ifThenElse(T t, T e);\n    }\n\n    class True extends Boolean {\n      T ifThenElse(T t, T e) {\n        return t;\n      }\n    }\n\n    class False extends Boolean {\n      T ifThenElse(T t, T e) {\n        return e;\n      }\n    }\n</code></pre>\nThere&#x27;s a slight wrinkle here, since calling &#x27;ifThenElse(foo, bar)&#x27; will execute <i>both</i> &#x27;foo&#x27; and &#x27;bar&#x27;; we&#x27;ll just get one of them returned back to us. If this is a problem, we can wrap our branches in zero-argument functions, pass those to &#x27;ifThenElse&#x27;, and call whichever function gets returned. Note that this is actually how Smalltalk implements boolean branching! <a href="https:&#x2F;&#x2F;rosettacode.org&#x2F;wiki&#x2F;Conditional_structures#Smalltalk" rel="nofollow">https:&#x2F;&#x2F;rosettacode.org&#x2F;wiki&#x2F;Conditional_structures#Smalltal...</a><p>Hopefully I&#x27;ve demonstrated that the three classed defined above are a <i>complete</i> implementation of booleans: we have the constructors (&#x27;new True()&#x27; and &#x27;new False()&#x27;), the destructor &#x27;ifThenElse(thenBranch, elseBranch)&#x27;, and <i>we don&#x27;t need anything else</i>. To drive this point home, here&#x27;s how we can define boolean algebra, translated from the above:<p><pre><code>    &#x2F;&#x2F; not(x)\n    x.ifThenElse(new False(), new True())\n\n    &#x2F;&#x2F; and(x, y)\n    x.ifThenElse(y, new False())\n\n    &#x2F;&#x2F; or(x, y)\n    x.ifThenElse(new True(), y)\n</code></pre>\nThis implementation of Boolean is a rather simple form of &quot;visitor pattern&quot;: the implementation of the &quot;ifThenElse algorithm&quot; is spread out amongst different implementations of the method, where each subclass knows how to handle its own case, and we just dispatch on whatever Boolean object we happen to have.<p>The point of Church Encoding is that we don&#x27;t actually need these classes and polymorphism at all: rather than wrapping up these methods into classes, defining a class hierarchy, constructing instances of these subclasses, invoking methods on those instances, dynamically dispatching on the vtables, etc.; we can just pass the functions around directly!<p>Switching to JS, since it has first-class functions, here&#x27;s my first example again:<p><pre><code>    const  trueIfThenElse = (t, e) =&gt; t;\n    const falseIfThenElse = (t, e) =&gt; e;\n\n    function1(...) {\n      FOO\n      return trueIfThenElse;\n    }\n\n    function2(...) {\n       BAR\n       function1(...)(BAZ, QUUX)\n    }\n</code></pre>\nIf we want to avoid executing both BAZ and QUUX, we could wrap them up in functions like &#x27;function1(...)(() =&gt; BAZ, () =&gt; QUUX)()&#x27;. We could also rename these functions to simply &#x27;true&#x27; and &#x27;false&#x27;, since they&#x27;re completely equivalent to those values (although that would be a syntax error in JS).<p>So now we&#x27;ve seen that (a) booleans can be completely implemented using if&#x2F;then&#x2F;else (b) the behaviour of if&#x2F;then&#x2F;else can be implemented using subclass polymorphism (c) subclass polymorphism can be emulated by passing around first-class functions. Note that we could have skipped all the OOP stuff and gone straight to functions, but I thought it might help some people, and it&#x27;s also interesting in its own right.<p>This also extends to sum types with any number of distinct forms (which we now know are &quot;constructors&quot;). The rule is simple: a type with N constructors can be represented as a function which takes N arguments, and returns one of them. For example, we could represent Colour, with Red&#x2F;Green&#x2F;Blue like this:<p><pre><code>    const red   = (r, g, b) =&gt; r;\n    const green = (r, g, b) =&gt; g;\n    const blue  = (r, g, b) =&gt; b;\n\n    function printColour(c) {\n      console.log(c(&quot;Received red&quot;, &quot;Given green&quot;, &quot;Bestowed with blue&quot;));\n    }\n</code></pre>\nThere are two other sorts of data to consider:<p>&quot;Product types&quot; contain multiple sub-values, e.g. &#x27;Coordinate(x, y, z)&#x27;. For these, the rule is that we <i>call the corresponding argument as a function</i>, passing it the sub-values as arguments. For example:<p><pre><code>    const mkCoord = (x, y, z) =&gt; f =&gt; f(x, y, z);\n\n    function showCoord(c) {\n      c((x, y, z) =&gt; console.log(\n        &quot;x: &quot; + x.toString + &quot; y:&quot; + y.toString + &quot; z: &quot; + z.toString\n      ));\n    }\n\n    const origin = mkCoord(0, 0, 0);\n    showCoord(origin);\n</code></pre>\nNote that I&#x27;m using raw JS numbers and strings for simplicity; we can implement these using Church Encoding (e.g. using 64 booleans to emulate a double-precision float), but it would be tedious for this example.<p>We can combine sums and products, i.e. each constructor can contain sub-values. This is what the &quot;Shape&quot; example from the article does. We just need to combine the two rules: take N arguments (once for each constructor), and call the appropriate argument with the sub-values. For example:<p><pre><code>    const circle = (x, y, r) =&gt; (ifCirc, ifRect) =&gt; ifCirc(x, y, z)\n\n    const rectangle = (x, y, w, h) =&gt; (ifCirc, ifRect) =&gt; ifRect(x, y, w, h)\n\n    const unitCircle = circle(0, 0, 1);\n\n    const unitSquare = rectangle(0, 0, 1, 1);\n\n    function drawShape(s) {\n      s(\n        (x, y, r)    =&gt; console.log(&quot;Circle of radius &quot; + r.toString),\n        (x, y, w, h) =&gt; console.log(&quot;Rect of area &quot; (w * h).toString)\n      );\n    }\n</code></pre>\nThe final possibility is recursive data, where the sub-values can be of the same type we&#x27;re defining. The article uses a binary tree as an example, but a list is easier. In OOP:<p><pre><code>    abstract class List&lt;T&gt; {\n      U reduce(U init, Function&lt;U, Pair&lt;U, T&gt;&gt; f);\n    }\n\n    class Nil&lt;T&gt; extends List&lt;T&gt; {\n      U reduce(U init, Function&lt;U, Pair&lt;U, T&gt;&gt; f) {\n        return init;\n      }\n    }\n\n    class Cons&lt;T&gt; extends List&lt;T&gt; {\n      private      T  head;\n      private List&lt;T&gt; tail;\n\n      public Cons(T head, List&lt;T&gt; tail) {\n        this.head = head;\n        this.tail = tail;\n      }\n\n      U reduce(U init, Function&lt;U, Pair&lt;U, T&gt;&gt; f) {\n        return this.tail.reduce(\n          f(new Pair&lt;U, T&gt;(init, this.head)),\n          f\n        );\n      }\n    }\n</code></pre>\nWith first-class functions (this might be slightly off; it&#x27;s been a while!):<p><pre><code>    const nil  = (ifNil, ifCons) =&gt; ifNil\n\n    const cons = (head, tail) =&gt; (ifNil, ifCons) =&gt; ifCons(\n      head,\n      tail(ifNil, ifCons)\n    );\n\n    const oneTwoThree = cons(1, cons(2, cons(3, nil)));\n\n    const plus = (x, y) =&gt; x + y;\n\n    function sum(lst) {\n      return lst(0, plus);\n    }\n\n    console.log(sum(oneTwoThree).toString);\n</code></pre>\nSo the trick to recursive data is that whenever we need to pass a sub-value to one of our N given functions, if that sub-value is of our recursive type (like the &#x27;tail&#x27; of a list is another list) then we first <i>call that sub-value with the same N functions we&#x27;ve been given</i>. That way, the structure &#x27;reduces&#x27; down to a single result.')
